# Personalized PDF watermark

The final MVC PDF file-response boundary adds a subtle diagonal `CONFIDENTIAL`, the authenticated account name (or safe account identifier), and the access time in UTC to every supported page. No controller action, report calculation/query, authentication policy, ownership check, database object, route, filename, view or frontend asset changes.

## Architecture

- `IPdfWatermarkService` / `PdfWatermarkService` edit a private in-memory copy using the existing **PDFsharp-MigraDoc 6.2.4**, whose package declares **MIT** licensing. No package was added.
- `PdfWatermarkResultFilter` is a normal MVC result filter, registered by `AddPdfWatermarks` in Program. It runs after existing action/authorization processing, only for authenticated, successful PDF file results. It is not an authorization filter and does not run as an always-run filter after access denials.
- PDF classification uses PDF MIME type or `.pdf` download/physical filename, case-insensitively. This covers the Admin generic-octet-stream download as well as explicit PDF responses.
- Non-PDF results and unsuccessful/anonymous results pass through unchanged. All current supported private PDF endpoints already require authorization. No public/anonymous PDF endpoint or alternative private-file route was introduced.
- Original bytes, files and report generators are not edited. Output is a new `FileContentResult`, retaining the existing inline/attachment filename behavior.
- A separate balanced graphics state, unique resource names and standard Helvetica font avoid changing the existing global report font resolver or original page streams. Page count, media/crop boxes and rotation are retained.
- Standard PDF font text is deliberately ASCII. Printable account names up to 64 characters are used directly; other names use the authenticated account ID, or its stable SHA-256-derived identifier when necessary. This avoids broken Arabic/non-Latin glyphs while retaining personalization. No other user's information is queried.
- Time comes from injected `TimeProvider`, once per response, and is labelled UTC. Each download is generated independently. There is no PDF response cache or per-user/shared watermark cache.

## Failure and privacy behavior

Input is limited to **20 MiB**, **500 pages**, and finite visible page dimensions of at least 72 points with enough space for the account/time text at six points or larger. Placement uses the intersection of media/crop boxes without changing either. Two parser operations may run concurrently. Encrypted/password-protected, detected signature-bearing, damaged/unreadable and unsupported PDFs are rejected. This avoids invalidating signatures or silently serving unwatermarked sensitive content.

Failure yields **422 Problem Details**, with no original PDF bytes. Source streams are disposed. Logs include only the failure exception type, not the document path, username, contents or parser exception message. Cancellation propagates rather than falling back. Fatal process failures are not disguised as successful downloads.

Personalized PDF responses have `private, no-store, max-age=0`, no-cache legacy headers and nosniff. Original ETag/Last-Modified and range-processing metadata cannot describe regenerated bytes, so the transformed response does not reuse them. Range/conditional requests receive the complete new PDF, not a byte slice or 304 from the original file. This is intentional for per-access timestamps and cross-user privacy.

No original uploaded file is overwritten, decrypted in storage or replaced. Existing private storage and authorized document lookup remain unchanged.

## Unsupported cases and limits

- Encrypted and detected signed PDFs, inputs above the limits, malformed files and unsupported page dimensions receive 422. There is no unwatermarked fallback.
- Current endpoints use FileContentResult, FileStreamResult or PhysicalFileResult; all are handled. A future VirtualFileResult PDF is deliberately rejected until safe provider-based handling is implemented. There is no such PDF endpoint in the inspected project.
- Static files, remote/external PDFs and documents opened outside MVC are outside the filter. No static private-PDF route was found/added.
- PDFsharp's parser is synchronous and not a process sandbox. Byte/page/concurrency bounds are not a guarantee against every pathological compressed PDF, parser defect or expensive input. Process-isolated parsing and document sanitization would be a separate, explicitly scoped hardening task.
- This is visual traceability, not DRM, a digital signature or a tamper-proof audit trail. It does not claim PDF/A recertification or full accessibility tagging preservation. The optional logo was omitted to keep the overlay small and avoid asset/font dependencies.

## Verification

- Application build: passed, zero errors/warnings.
- **50 database-free feature checks:** every page/user/UTC label; source bytes; mixed portrait/landscape/cropped/rotated pages; existing supplier/report generators; per-user separation; safe identifiers; malformed/protected/signature-bearing/oversized/excess-page input; cancellation; content/stream/physical results; generic MIME download; stream disposal; inline/attachment behavior; no-store; non-PDF and denied-response preservation.
- **30 isolated HTTP checks:** content/stream/physical PDF execution, filenames/inline behavior, cache/range/conditional handling, authenticated/anonymous/wrong-role behavior, controlled 422 failure, unchanged CSV/XLSX/PNG/DOCX bodies, anonymous denial on all seven original role dashboards, and anonymous denial on all seven existing PDF route/preview cases.
- **24 existing reporting checks:** passed against the current compiled application, including SQL query translation without connecting, scope, decision timestamps, formula-like Excel text, four-section/sheet content and large/empty output.
- **31 existing award notification checks:** passed against the current compiled application, using the existing database-free memory store; no award/recipient logic changes.
- Poppler rendered all three mixed-page fixtures plus actual report-generator and supplier-generator output; inspected portrait and cropped/rotated pages and representative report/summary pages. Original content remained legible beneath the light overlay. Poppler emitted local fallback-font notices for Symbol/ArialUnicode, but generated the inspected images successfully.
- Synthetic artifacts are outside the repository under `%TEMP%/pdf-watermark-artifacts`. HTTP fixtures use a separate ephemeral host, not real database users/files. No application startup seeding or database access was executed by the watermark tests.
- Live SQL-backed positive downloads under every business role, arbitrary third-party PDF compatibility, physical devices, PDF/A certification, very large hostile-parser stress tests and true digital-signature validation were not performed. HTTP access denials and unchanged controller source do not substitute for a full ownership penetration test.

Feature tests can be invoked from an external harness via `PdfWatermarkChecks.RunAsync(outputDirectory)`, without starting the application or connecting to a database. Existing tests are unchanged. No business, schema, authentication or approval-only workflow change is part of this feature.
